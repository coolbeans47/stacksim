# Private Notes: an authenticated application

Learn sign-up, SRP sign-in, record ownership, realtime authorization, and the
separate Identity Pool/IAM flow with unmodified Amplify clients. This example
uses two exact generated backends from the repository's frozen fixtures:

| App mode | Backend fixture | What access means |
| --- | --- | --- |
| Private records | `test/fixtures/amplify-gen2-auth-data-owner` | A Cognito User Pool token and generated owner rule authorize each record. |
| Shared signed-in records | `test/fixtures/amplify-gen2-auth-data-iam` | Identity Pool credentials sign Data requests with IAM. All authenticated users share the model. Guests are denied. |

The model is named `Todo` in the generated schema; the UI presents its title and
description as notes. The app does not filter out other owners itself. The
unchanged generated resolvers and DynamoDB conditions enforce access.

Pinned frontend packages: `aws-amplify@6.20.0`, React/React DOM `19.1.1`, Vite
`8.1.5`, and `@vitejs/plugin-react@6.0.4`. Both backend fixtures pin
`@aws-amplify/backend@1.24.0`, `@aws-amplify/backend-cli@1.9.0`, and CDK `2.265.0`.
Use Node.js 22.13 or later. This is the exact local Auth + scalar Data slice;
it does not claim unrestricted Amplify support, group authorization, social
providers, advanced MFA, Storage, user Functions, or Hosting.

## Start the lab

In a terminal at the StackSim repository root:

```sh
npm ci
npm run build
npm run start:amplify
```

Keep StackSim running. Its control endpoint and console are on
[127.0.0.1:4566](http://127.0.0.1:4566/_stacksim/console). The AppSync HTTP and
realtime endpoints use local TLS. Trust the CA generated by this simulator
in your browser/OS trust store before using Data or subscriptions. The CA is
available at [the local CA download](http://127.0.0.1:4566/_stacksim/appsync/ca.pem)
and `.stacksim/data/cloudformation/custom-resource-pki/ca.pem`.

On macOS, import it into Keychain Access and trust it for SSL. On Windows,
import it into the current user's Trusted Root Certification Authorities.
On Linux, use your browser's Authorities certificate import or the system
trust-store workflow for your distribution. Restart the browser after import.
Only trust the CA from this local simulator; do not disable TLS verification.

In another terminal:

```sh
cd examples/amplify-auth-notes
npm ci
npm run backend:install
npm run deploy
npm start
```

Open [the owner application](http://127.0.0.1:5173/?mode=owner). The `deploy`
script invokes the unmodified pinned `ampx sandbox --once --identifier
authnotes` separately in each fixture directory. The CLI writes its original
outputs into `outputs/owner/amplify_outputs.json` and
`outputs/iam/amplify_outputs.json` using `--outputs-out-dir`. No template,
dependency, resolver, or CLI output is patched. Keep the fixture package names
and backend source unchanged for this frozen experiment.

## Alice and Bob: ownership and realtime

1. Open the owner application in two separate browser profiles (or one normal
   and one private profile). Two tabs in the same profile share Auth storage.
2. In Alice's profile, choose **Sign up**, use `alice@example.test`, and choose
   a password with uppercase, lowercase, a number, and a symbol. The password
   stays in the input only until the request completes.
3. Open the StackSim console and sign in with local access key `admin` and
   secret key `password`. Open **SES → Inbox**, select Alice's confirmation
   email, and copy its six-digit code into the app's **Confirm** tab. Codes
   are read through this existing developer-safe mailbox, not a new bypass.
4. Sign Alice in. Repeat sign-up, confirmation, and sign-in for
   `bob@example.test` in Bob's profile. The active email and `userPool` mode
   are always visible above the workspace.
5. Create several Alice notes. Create a Bob note. Each profile lists its own
   records, including when filtering titles or selecting **Load next page**.
   The generated owner field is stamped by the backend.
6. Copy an Alice note id with **Copy ID**. Paste it into Bob's **Can Bob get
   in?** panel. Try **Get**, **Update**, and **Delete**. The record is not
   returned, and changes are denied. Confirm Alice can still read and modify
   her note. Those buttons make actual API requests; use an id from the other
   user, since an operation on your own id is allowed.
7. Keep both profiles open. Create, complete, reopen, and delete notes. The
   **Authorized updates** panel shows only changes authorized for that owner.
   Alice's updates must not appear in Bob's feed, and vice versa. Create a
   fresh note after both profiles say a subscription was requested.
8. Select **Refresh & reconnect**. Amplify refreshes the session and the app
   reconnects the subscriptions for the same user. Select **Sign out
   locally**: records and subscriptions are immediately cleared. Sign in as
   the other user in that profile and verify the list and event feed belong
   to the new user.

The browser never renders tokens, passwords, secret keys, or session tokens in
the session panel or event diagnostics. Password inputs are masked; avoid
including credentials or confirmation emails in screenshots. Amplify manages
its normal browser session storage. Local sign-out disposes of that frontend
session; it does not claim to revoke every previously issued offline JWT or
unexpired STS credential on the server.

## Identity Pools and IAM are a separate experiment

Select **Shared signed-in records**. Switching modes signs out of the previous
frontend session and opens the other fixture's unchanged outputs.

1. While signed out, choose **Test guest Data access**. Amplify can obtain guest
   Identity Pool credentials, but those credentials cannot call this
   authenticated-only model.
2. Sign up and confirm a user in this mode. The fixtures have separate User
   Pools, so registration in owner mode does not create an IAM-mode user.
3. Sign in and create/read/update/delete shared notes. The app uses
   `authMode: 'identityPool'`; the same Amplify Auth session obtains temporary
   Identity Pool credentials and the unmodified Data client signs requests.
   A second authenticated user can see these notes. This rule proves IAM
   authorization, not owner isolation.
4. Select **Try the adjacent owner API**. The session's generated IAM role
   permits this fixture's Data API; it has no grant on the separate owner API.
   The attempted request is denied. Deploy both fixtures for this check.
5. Sign out and select **Test guest Data access** again. The new guest session
   is denied and does not reuse authenticated credentials. Previously issued
   STS credentials retain their normal one-hour validity; disposing of the
   frontend session and expiring server credentials are different events.

User Pools answer who signed in by issuing JWTs. Identity Pools exchange a
verified login for role credentials. IAM decides which AWS API resources and
fields that role can call. The generated owner rule decides which private
records a signed-in person may access. The UI clearly separates these modes.

## Endpoint routing and local-only operation

The browser consumes CLI-written outputs unchanged. `src/configure.mjs` uses
the pinned Amplify library's public `Auth.Cognito.userPoolEndpoint` and
`Auth.Cognito.identityPoolEndpoint` configuration fields to select StackSim's
regional SDK routes. It does not rely on browser support for `AWS_ENDPOINT_URL`.
The AppSync URL comes directly from the CLI output and must also be loopback.

The deployment wrapper clears inherited AWS credentials/profiles/endpoints and
proxy settings, supplies local defaults, disables Amplify/CDK telemetry,
serves optional notices from a local server, and loads the repository's
network tripwire into the CLI subprocess tree. Only the selected control and
notices loopback ports are admitted. Package installation is a separate step
and uses npm's ordinary registry access.

To inspect routing, open browser developer tools → Network. Auth requests use
`/_stacksim/cognito-idp/eu-west-1/sdk`, credential requests use
`/_stacksim/cognito-identity/eu-west-1/sdk`, and Data HTTP/WebSocket requests
use the generated local AppSync URL. Do not export request headers or bodies:
the browser's normal network inspector can show the credentials it transmits.

The default backend control endpoint is `http://127.0.0.1:4566`. To use a
different loopback control origin, set `STACKSIM_ENDPOINT` for the deployment
wrapper and put the matching `VITE_STACKSIM_ENDPOINT` in `.env.local` for Vite,
then redeploy. Only loopback origins are accepted. Keep the frontend on HTTP
loopback when its Cognito endpoint uses HTTP; browser mixed-content rules still
apply. The wrapper fixes account `000000000000` and Region `eu-west-1`.

## Cleanup and repeat

Sign out of both browser profiles and run:

```sh
npm run backend:delete
```

Confirm the CLI's deletion prompts for the two `authnotes` sandboxes. Deletion
removes their users and records; it preserves other sandboxes and shared
bootstrap resources. The wrapper removes each mode's local outputs only after
its CLI deletion succeeds. Wait at least 30 seconds before deploying the same
sandbox identifier again: Parameter Store preserves its normal name-reuse
cooldown for the generated reference parameter. To repeat, run `npm run deploy`, reload both
profiles, and register users again. Old outputs cannot make a deleted pool or
API work.

| Command | Purpose |
| --- | --- |
| `npm run backend:install` | Install each frozen backend from its lockfile. |
| `npm run deploy` | Deploy owner and IAM fixtures and write both outputs. |
| `npm run deploy:owner` / `npm run deploy:iam` | Redeploy one mode. |
| `npm start` | Run the frontend at port 5173. |
| `npm run build` | Build the frontend and copy existing outputs unchanged. |
| `npm run preview` | Preview that build at port 4173. |
| `npm run backend:delete` | Delete both lab sandboxes after CLI confirmation. |

If a Data/subscription request fails, first check that StackSim was started
with `start:amplify`, the local CA is trusted, and the outputs match the current
deployment. Re-run deployment if resource ids or the local TLS port changed.
Do not edit the output file to work around a stale deployment. The broader
implementation/test boundary is recorded in
[`docs/gap-3-authenticated-app-closeout.md`](../../docs/gap-3-authenticated-app-closeout.md).


The recorded [browser smoke evidence](evidence/browser-smoke.json) covers the
two modes with Chromium 149, Node 22.13, the pinned clients, and only loopback
browser requests. It includes simultaneous owner profiles, deliberate denials,
refresh/reconnect, user switching, and repeat sign-in after simulator restart.
The fixture integration tests cover backend lifecycle; this browser artifact
records the actual learning UI walkthrough without secrets or request payloads.
